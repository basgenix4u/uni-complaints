# Deploying to Vercel, Render and Supabase

Yes, this combination works. The frontend is a static build, the backend is
a container, and Supabase provides Postgres and file storage.

There are four things that will catch you out, and all four are handled in
the repository already. They are called out below so you know why a setting
is what it is.

| Trap | Why it bites | Handled by |
|---|---|---|
| Supabase direct connection is **IPv6 only** on the free plan | Render is IPv4, so a direct URL never connects | Use the **session pooler** URL, port 5432 |
| Render's filesystem is **ephemeral** | Uploaded evidence disappears on the next deploy | Cloudinary or Supabase Storage |
| Rate limits are counted **per worker** | Ten login attempts becomes ten per worker | Redis, and the app refuses to start without it |
| The frontend calls a **relative** `/api` | On Vercel that hits Vercel, not Render | Set `VITE_API_URL` |

Work through the parts in order. Supabase first, because the other two need
its values.

---

## 1. Supabase

### Create the project
1. New project. Choose a region close to your users — **Frankfurt** is
   usually the best latency for Nigeria among the European options.
2. Save the database password somewhere safe. It is shown once.

### Get the right connection string
Click **Connect** at the top of the dashboard.

> **Take the Session pooler string, not the direct connection.**
>
> The direct connection (`db.<ref>.supabase.co:5432`) is IPv6 only on the
> free plan. Render is IPv4, so it will fail to connect with a timeout that
> looks like a firewall problem. The shared pooler is IPv4 on every plan.

It looks like:

```
postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Keep port **5432** (session mode). Transaction mode on 6543 also works and
the application detects it and adjusts, but session mode is the better fit
for a long-running container.

> Supabase Storage is not needed if you use Cloudinary for attachments.
> Pick one; see part 2.

---

## 2. Attachments

Render's filesystem is ephemeral, so uploads must go somewhere else or
they disappear on the next deploy. Either provider works, and the
application picks whichever is configured. Cloudinary wins if both are.

### Cloudinary

1. Sign up and open the dashboard.
2. Copy **Cloud name**, **API Key** and **API Secret** from Product
   Environment Credentials.

| Variable | Value |
|---|---|
| `CLOUDINARY_CLOUD_NAME` | Your cloud name |
| `CLOUDINARY_API_KEY` | API key |
| `CLOUDINARY_API_SECRET` | API secret |
| `CLOUDINARY_FOLDER` | `resolve/attachments` |

There is nothing else to configure. No bucket, no preset, no CORS rule.

> **Why you do not need to set anything to make it private.**
>
> Cloudinary's default delivery type is `upload`, which puts the asset on
> a public CDN. For ordinary product images that is the point; for a
> photograph attached to a harassment complaint it is a data breach.
>
> Every upload from this application sets the delivery type to
> `authenticated`, so the original and every derived version require a
> signed request. The API fetches the bytes with a short-lived signed URL
> and streams them to the caller only after the same permission checks as
> before. **No Cloudinary URL ever reaches a browser**, so a shared link
> exposes nothing.
>
> This is not optional or configurable, because getting it wrong is
> silent: a public asset works perfectly and simply publishes evidence.

The free tier covers roughly 25 GB of storage and bandwidth per month,
which is generous for documents and photographs.

### Supabase Storage, as an alternative

1. **Storage → New bucket**, name it `attachments`
2. **Leave "Public bucket" switched off**
3. From **Settings → API**, take `SUPABASE_URL` and the **service_role**
   key

> The service_role key bypasses row level security. It belongs on the
> server only. Never put it in the frontend or in a `VITE_` variable.

## 3. Render

### Deploy
1. **New → Blueprint**, point at this repository.
2. Render reads `render.yaml` and creates: the API, three scheduled jobs,
   and a Redis instance.
3. Fill in the values it marks as required:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The session pooler string from part 1 |
| `CLOUDINARY_CLOUD_NAME` | From part 2, if using Cloudinary |
| `CLOUDINARY_API_KEY` | From part 2 |
| `CLOUDINARY_API_SECRET` | From part 2 |
| `SUPABASE_URL` | Only if using Supabase Storage instead |
| `SUPABASE_SERVICE_KEY` | Only if using Supabase Storage instead |
| `CORS_ORIGINS` | Your Vercel URL, once you have it in part 4 |
| `APP_URL` | The same Vercel URL. Password reset links point here |

`SECRET_KEY` and `JWT_SECRET_KEY` are generated by Render. `RATELIMIT_STORAGE_URI`
is wired to Redis automatically.

Email and SMS can be left empty at first. Messages queue rather than being
discarded, and send once you configure a provider.

### What happens on deploy
The container runs `flask db upgrade` before starting workers, so the
schema is created on the first deploy and migrated on later ones. You do
not run migrations by hand.

### Create the first administrator
Once the deploy is green, open **Shell** on the API service:

```bash
flask seed
```

That creates the platform administrator from `PLATFORM_ADMIN_EMAIL` and
`PLATFORM_ADMIN_PASSWORD`. Set those two variables first, and **change the
password immediately after signing in**.

Do not use `--demo` on production; it creates a fictional university.

### A note on the free plan
Render's free web services sleep after inactivity, and the first request
afterwards takes around fifty seconds. For anything real, use the starter
plan. Cron jobs are not available on free at all, so escalation and email
delivery would never run.

## 4. Vercel

### Deploy
1. **New Project**, import this repository.
2. Set **Root Directory** to `frontend`. Vercel will otherwise try to build
   the whole repository and fail on the Python.
3. The framework is detected as Vite. `vercel.json` supplies the rest.

### One environment variable

| Variable | Value |
|---|---|
| `VITE_API_URL` | `https://resolve-api.onrender.com/api` |

> This is the trap most people hit. The client defaults to a relative
> `/api`, which is right for local development where Vite proxies to the
> backend. On Vercel there is no backend to proxy to, so the request goes
> to `your-app.vercel.app/api` and returns the index page. Every call then
> fails with a confusing parse error rather than a network error.
>
> Note the `/api` suffix. The value is the base of the API, not the host.

Vite inlines this at build time, so **redeploy after changing it**.

### Close the loop
Go back to Render and set `CORS_ORIGINS` and `APP_URL` to your Vercel URL.
Until you do, the browser blocks every request and the console shows a CORS
error.

### Preview deployments, if you use them
Each preview gets a unique hostname, so they cannot be listed. Set this on
Render instead:

```
CORS_ORIGIN_REGEX=https://.*\.vercel\.app
```

Leave it unset if you only deploy production.

## Every variable, in one place

Copy this when filling in Render. Values you generate or paste are marked.

```bash
# --- Database (part 1) -------------------------------------------
# SESSION POOLER string, port 5432. Not the direct connection.
DATABASE_URL=postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres

# --- Attachments (part 2) ----------------------------------------
CLOUDINARY_CLOUD_NAME=<cloud name>
CLOUDINARY_API_KEY=<api key>
CLOUDINARY_API_SECRET=<api secret>
CLOUDINARY_FOLDER=resolve/attachments

# --- Where the frontend lives (part 4) ---------------------------
CORS_ORIGINS=https://<your-app>.vercel.app
APP_URL=https://<your-app>.vercel.app

# --- First administrator, used once by `flask seed` --------------
PLATFORM_ADMIN_EMAIL=you@yourdomain.ng
PLATFORM_ADMIN_PASSWORD=<a strong password you change after first sign in>

# --- Generated by Render, do not set by hand ---------------------
# SECRET_KEY, JWT_SECRET_KEY, RATELIMIT_STORAGE_URI

# --- Optional. Leave empty and nothing breaks --------------------
SMTP_HOST=
SMTP_PORT=587
SMTP_USERNAME=
SMTP_PASSWORD=
MAIL_FROM=no-reply@yourdomain.ng
SMS_PROVIDER=
TERMII_API_KEY=
SENTRY_DSN=
```

On **Vercel**, one variable only:

```bash
VITE_API_URL=https://resolve-api.onrender.com/api
```

## 5. Check it works

```bash
# The API is up and the database answers
curl https://resolve-api.onrender.com/api/ready
# {"status":"ready","success":true}

# Every response carries a traceable id
curl -sD - -o /dev/null https://resolve-api.onrender.com/api/health | grep -i x-request-id
```

Then in the browser:

1. Open the Vercel URL. The sign-in page loads.
2. Sign in as the platform administrator.
3. Create an institution. Departments are created with it.
4. Register a student against that institution.
5. File a complaint. **The receipt shows a ticket number and a deadline.**
6. Attach a photograph, then download it again. This proves storage works;
   it is the step that fails silently if storage is misconfigured.
   If you use Cloudinary, open the asset in the Media Library and confirm
   its delivery type reads **authenticated**, not **upload**. Pasting its
   URL into a private browser window should be refused.
7. As staff, open the complaint, reply, and resolve it.

If step 6 works, the ephemeral filesystem problem is genuinely solved.

## When something is wrong

| Symptom | Cause | Fix |
|---|---|---|
| API will not start, logs mention rate limiting | Redis not wired | Check `RATELIMIT_STORAGE_URI` points at the Render Redis |
| API will not start, logs mention `SECRET_KEY` | A development default reached production | Let Render generate it |
| Database connection times out | Using the direct IPv6 URL | Switch to the session pooler string |
| Frontend loads but every call fails | `VITE_API_URL` missing or without `/api` | Set it and **redeploy** |
| Browser console shows a CORS error | `CORS_ORIGINS` does not match the Vercel URL exactly | Include the scheme, no trailing slash |
| Uploads succeed then 404 on download | Wrong credentials, or the folder changed after files were stored | Check the three Cloudinary values, or `SUPABASE_BUCKET` and that the key is service_role |
| Cloudinary returns 401 on upload | API secret wrong, or the server clock is far off | Re-copy the secret. Signatures include a timestamp |
| Emails never arrive | No SMTP configured | Set `SMTP_*`. Nothing was lost; the queue holds them |
| First request each morning is slow | Free plan sleeping | Move to starter |

### Reading the logs

Every response carries `X-Request-ID`, and every error returns it as
`reference`. When someone reports a problem, ask for that value:

```
Render → your service → Logs → search the reference
```

That finds the exact request, its route, status, duration and stack trace.

## What this costs

| Service | Free | Realistic |
|---|---|---|
| Vercel | Enough for the frontend | Free |
| Render web | Sleeps, no cron | Starter, about $7/month |
| Render Redis | 25 MB | Starter, about $10/month |
| Supabase | 500 MB database, 1 GB storage | Free to start |

Around **$17 a month** for something that stays awake and runs its
scheduled jobs. The free tier is fine for a demonstration but will not
escalate an overdue complaint, because cron does not run.

Deployment is not launch. Still outstanding, and none of it is code:

- A practitioner reviews `docs/PRIVACY-POLICY.md` and
  `docs/RECORD-OF-PROCESSING.md`
- A Data Protection Officer is appointed
- Whether NDPC registration is triggered is assessed

  takes daily backups on paid plans; on free you should export regularly
  yourself. An untested backup is a hope
